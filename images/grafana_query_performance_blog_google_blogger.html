Tracking Query Performance Across 50+ Grafana Dashboards: A Data-Driven Approach

Executive Summary

In enterprise environments with dozens of Grafana dashboards, identifying and resolving performance bottlenecks becomes a critical challenge. This project implements an automated query performance tracking system that monitors PostgreSQL query execution times across 50+ Grafana dashboards, providing actionable insights to optimize database performance and improve user experience.

Key Achievement: Transformed reactive performance troubleshooting into proactive, data-driven optimization across an entire enterprise Grafana deployment.

The Challenge

Managing a large Grafana deployment presents several performance challenges:

  • Scale: 50+ dashboards with hundreds of panels and variables
  • Visibility Gap: No centralized view of slow-running queries
  • User Impact: Slow dashboards lead to poor user experience and reduced adoption
  • Resource Waste: Inefficient queries consuming unnecessary database resources
  • Reactive Approach: Performance issues discovered only when users complain

The Solution: Automated Query Performance Tracking

Architecture Overview

The solution consists of three key components working together to provide comprehensive performance visibility:

1. Data Collection Script

snapshot_query_perf.py

  • Leverages PostgreSQL's pg_stat_statements extension
  • Extracts Grafana-tagged queries with performance metrics
  • Runs on a scheduled basis (Azure Functions or cron)
  • Stores historical snapshots for trend analysis

2. Performance History Database

query_perf_history table

  • Stores time-series performance data
  • Tracks: execution time, call frequency, standard deviation
  • Enables historical trend analysis
  • Supports anomaly detection

3. Grafana Health Dashboard

JSON configuration

  • Real-time monitoring of query performance
  • Identifies optimization backlog
  • Surfaces top offenders and trends
  • Provides drill-down capabilities

Technical Implementation

1. Query Performance Collector

# Core functionality: Extract Grafana queries from pg_stat_statements
_SNAPSHOT_QUERY = """
    SELECT
        trim(substring(query FROM '@grafana[^*]+')) AS tag,
        SUM(calls) AS calls,
        AVG(mean_exec_time) AS mean_exec_time,
        MAX(max_exec_time) AS max_exec_time
    FROM pg_stat_statements
    WHERE query ILIKE '%@grafana%'
    GROUP BY tag
"""

Key Features:

  • Uses query comments (@grafana/dashboard_uid/panel_id) for traceability
  • Aggregates metrics across query variations
  • Captures standard deviation for consistency analysis
  • Automatically scheduled execution with error handling

2. Database Schema

The query_perf_history table stores:

Field Description
tag Grafana dashboard and panel identifier
snapshot_time Timestamp of data collection
calls Number of query executions
mean_exec_time Average execution time (ms)
max_exec_time Peak execution time (ms)
stddev_exec_time Standard deviation (variability indicator)
wal_bytes Write-ahead log usage
rows Total rows processed

Key Metrics and Insights

Performance Thresholds

The system uses configurable thresholds to identify issues:

Metric Threshold Impact
Slow Query Mean execution time > 5 seconds User-noticeable delay
Chatty Dashboard High call frequency + elevated latency Database overload
Long-Running Active Queries executing > 30 seconds Resource contention

Optimization Prioritization

Queries are prioritized using a weighted formula:

Priority Score = Call Count × Average Execution Time

This ensures focus on:

  1. High-impact optimizations (frequent + slow)
  2. User-facing performance improvements
  3. Maximum ROI on optimization efforts

Technical Challenges Overcome

❌ Challenge 1: Query Identification

Problem: Correlating PostgreSQL queries back to specific Grafana panels

✓ Solution: Implemented query tagging convention (@grafana/uid/panel_id)

❌ Challenge 2: Metric Aggregation

Problem: Multiple query variations for the same panel

✓ Solution: Used regex-based tag extraction and GROUP BY aggregation

❌ Challenge 3: Historical Analysis

Problem: pg_stat_statements cumulative since last reset

✓ Solution: Periodic snapshots with timestamps for trend analysis

❌ Challenge 4: Performance Impact

Problem: Monitoring system shouldn't impact performance

✓ Solution: Lightweight collector with indexed queries and scheduled execution

Getting Started

Prerequisites

  1. PostgreSQL with pg_stat_statements enabled
  2. Grafana with PostgreSQL datasource
  3. Python 3.8+ with SQLAlchemy

Quick Setup

# 1. Enable pg_stat_statements
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
SELECT pg_reload_conf();

# 2. Create history table
CREATE TABLE query_perf_history (
    id SERIAL PRIMARY KEY,
    tag TEXT NOT NULL,
    snapshot_time TIMESTAMPTZ NOT NULL,
    calls BIGINT,
    mean_exec_time DOUBLE PRECISION,
    stddev_exec_time DOUBLE PRECISION,
    max_exec_time DOUBLE PRECISION,
    wal_bytes BIGINT,
    rows BIGINT
);

# 3. Set environment variables
export _DB_SERVER="your-server"
export _DB_NAME="your-database"
export _DB_ADMIN_USER="your-user"
export _DB_ADMIN_PASSWORD="your-password"

# 4. Run collector
python snapshot_query_perf.py

# 5. Import Grafana dashboard
# Import "Grafana Health - Query Performance.json" via Grafana UI
