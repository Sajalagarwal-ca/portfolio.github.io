Turning daily snapshots into trusted data-quality insights

I built and stabilized a Power BI application-data-quality report so teams could assess application completeness and business-rule compliance across daily snapshots—not just a single day.

The challenge

The original report treated application ID as unique. When history was introduced, the same application appeared once per snapshot date. That broke the model’s key assumption and made it possible for historical rows to be joined or aggregated as if they belonged to one current snapshot.

Keys and relationships

Application IDs repeated across dates, preventing a valid one-to-many relationship at the new snapshot grain.

Cross-date lookups

Quality checks that reference completeness attributes needed to retrieve values from the matching snapshot.

Misleading totals

Some measures could aggregate multiple dates, while incomplete relationship paths repeated grand totals across attributes.

Refresh pressure

Large historical queries also needed careful date filtering and staged refresh optimization.

The solution

I treated the application on a given date as the reporting entity, then carried that grain consistently through source transformations, model relationships, measures, and validation.

  1. Created a composite snapshot key. Application ID plus snapshot date forms a unique AppKey, preserving history without collapsing multiple days into one record.
  2. Made Power Query date-aware. Source queries filter a configurable date range, deduplicate at the correct grain, normalize date types, and include snapshot date in related-field joins.
  3. Repaired filter paths. The model relates application snapshots to completeness and quality facts and connects the date dimension to the snapshot date.
  4. Added validation. Diagnostic measures check row counts, matching keys, and filter propagation; report checks confirm that attribute-level results are not simply repeated grand totals.
  5. Tuned refresh deliberately. Incremental Refresh and controlled query parallelism reduce unnecessary work, while database-side optimizations remain coordinated follow-ups.

How I validated it

  • Checked that application-snapshot keys match across related tables.
  • Confirmed completeness values vary by attribute instead of showing the same total on every row.
  • Verified that quality-rule lookups use the completeness value from the same snapshot date.
  • Used key-coverage diagnostics to surface missing source records for upstream investigation.
  • Tested date filtering against the intended snapshot.

Results and scope: The core snapshot-model fixes, date-aware transformations, relationship corrections, and diagnostics are implemented. No verified before/after refresh benchmark is available, so this case study makes no refresh-speed improvement claim.

What I learned

Model the true grain

If the source captures an entity once per day, the date is part of its identity for historical reporting.

Join on time as well as entity

Historical lookups must match both the business key and the snapshot date.

Prove filter behavior

Diagnostics and reconciliation checks expose modeling defects that a visual alone can hide.

Share performance ownership

Report-side tuning helps, but source indexing, capacity, and materialization may need database-owner support.

Follow-up work: The selected-snapshot DAX rewrite and some database/refresh work are documented as proposed or pending, not as completed changes.
